01挖需求

从社交媒体挖需求和趋势

常规做法看搜索指数、看榜单 —— 今天讲一个更快的：盯住社媒
热点来临之前→ 盯官方活动 · 现象级爆款→ 能和业务结合？能持续拿流量？怎么差异化？
  • 话题起势时「在场」 — ColorWalk 一词在小红书起热，预判流量窗口，五一出行季前上线
  • 评论区是需求金矿 — 用户的抱怨、晒图、@朋友，都是未满足的需求信号
  • Agent 做粗筛、人做判断 — Agent 跑调研和聚类降噪；要不要做，人拍板
热点来的时候，「在场」很重要。
真实收藏夹：日常刷到的需求信号，随手归档
01落库

及时收集落库：100 Bad Ideas

  • 一切 idea 默认是 bad — 不筛选、先落库，防止「灵感只活三分钟」
  • 每条 idea 的归宿 — 埋葬 / 孵化 / 继续观察，定期回顾
  • 个人是仓库，组织是灵感库 — 团队维度用一份共享文档管所有想法，谁看到都往里扔
  • ColorWander 就从这里长出来 — 文学时钟语料 × ColorWalk 热点，两条旧 idea 的组合
有效上下文不遗漏 —— Agent 记不住你没写下来的东西。
100 Bad Ideas · 真实仓库：多数想法的归宿是被划掉
01反馈进 Agent

反馈怎么进来：记录要无摩擦，落库靠 Agent

工具不重要，重要的是能无摩擦、高效、持续地记
  • 自动抓取 — 有官方 API 的渠道：邮件已自动建 issue；App Store 评论走 ASC API
  • 手动记录 — 微信群 / 小红书 / 抖音随手转发到一个固定地方（我用一个只有自己的微信群）
  • 持续和 Agent 聊 — 攒一批 → 一句「整理归档」→ Agent 去重、打标、建 issue、给老 issue 补档
无 API / 风控严的渠道人转发，有 API 的自动 —— 别为了「全自动」去碰平台风控。
我的「灵感收集」群：只有自己，随手扔

01排期

排期怎么做：一块本地看板，逐项拍板

排 v1.5 时的真实看板 —— 480 张票、255 open、20 张待聊；规划不靠聊天里的长列表
列 = 状态机（待开发 / 有遗留 / 待验收 / Done / Reject）· 卡片可拖改状态 · 「待聊」= Agent 写好的讨论抽屉 · 底部「决定」= 人拍板
一轮规划四步（kanban skill）
  • 对账补票：brief / 口述里有需求没票的，先建票再上板；冲突项、反向项单列
  • 刷新数据：gh 拉全部 issue 成 json，看板只认票号
  • 重灌讨论抽屉：Agent 把每张待拍板票的争议点、推荐（★）写进卡片
  • 逐项拍板 → 落账：人在板上点决定，复制贴回；Agent 批量改标签 / 挂 Milestone
为什么不用 GitHub 自带的 Projects
  • 看板是 Agent 写的一个自包含 HTML，永不上云，随手重生成
  • 讨论抽屉带着上下文来拍板，不是光看标题
  • 决定的是人，落账的是 Agent —— 20 张票一次贴回，不用一张张点

一次返回完整 comment

02原型验证

原型先跑一遍，感受完再做关键决策

批量处理 v1.5 · 可点的交互原型 + 需求决策页，都是 Agent 从 issue 长出来的
交互原型：多选 → 母版 → 应用全部 → 微调 → 导出，数据为模拟
需求决策页：可行性 / 风险表 / §1–§6 三案点选
  • 先走完整流程 — 在原型里把多选到导出点一遍，再回来拍 §1–§6
  • 决策页把「要不要」变成「选 A 还是 B」 — 每一案带工作量和取舍
  • 感受 → 决策 → Spec — 顺序不能反，否则 Spec 写的是想象
02方案评审

方案评审：可视化代替文本

来自大家的预习提问 ① —— 能点选的不用文字描述，能钉图钉的不打字

02我的做法

品味从外面灌进去：我的三个做法

动手前先定方向

Design.md + 关键页面 HTML，定稿前就是 Agent 的约束。再拿它对着 brief 复核：哪部分换个需求也会这么写，就重写。

给锚点，不给形容词

随手存好设计的截图；指名真实产品 / 风格流派。反例是我自己：只说了「深色、高级感」，拿到的就是暖黑 + 金 + 光晕全套。

截图闭环，写的不自评

代码侧 = 双 reviewer + /ship 门禁；设计侧目前靠人在真机上看。下一步：独立 design critic 只看截图打分，9/10 才停。

外部印证 —— OpenAI 叫 Visual thesis + token 五件套，Anthropic 官方 skill 叫 compact token system，Anshu 说的是委员会设计 —— 同一件事。
02留还是砍

看起来完美的细节：哪些必要，哪些多余

AI 只会做加法，不会做减法 —— 删代码对它是冒险，所以「删」必须由人发起
问 1
服务核心动线吗？

不在主路径上的细节，再精致也是装饰。

问 2
用户第二次还会注意吗？

只惊艳一次的效果换不来留存，只换来维护成本。

问 3
删掉有人会发现吗？

拿不准就删了看 —— 没人发现的细节就是多余的。

官方补一条
这个元素在说事，还是在装饰？

编号、描边、分割线、小标签都在向用户暗示一层意思：01 / 02 / 03 = 「有先后」，一圈描边 = 「这是一组」，本页左上角那行小字 = 「这是第二章」。加之前问一句：这层意思是真的吗？不是就删。动效同理，非用户触发的只留一处。

出门前照镜子，摘掉一件配饰 ——把大胆只花在一个地方，周围全部安静。

04埋点

埋点思路：跟着业务问题走

先画用户走过的每一站，再决定在哪一站埋什么 —— 旅程图是埋点的「需求文档」
每个事件回答一个问题

「用户卡在哪一站付费」值得埋；「点了哪个按钮」全埋 = 全没用

关键参数带上

曝光埋点带档位 / 来源 / 站点，出问题能回放，不用猜

脏数据提前防

开发机 / 模拟器的事件进了生产库，结论全歪；过滤规则第一天就写

埋点是给未来的自己留证据 —— 上线后想补，数据已经没了
v1.4.2 用户旅程图（Agent 出图、人裁定）：每一站的行为 / 弹窗触点 / 心里话 / 情绪 —— 埋点按站布
04看板

Agent 直接搭经营看板：想看什么，说一句

看板本身是 Agent 写的

一个本地 HTML 页面，接 PostHog + App Store API，刷新一条命令。

两套口径分开挂牌

埋点看行为、平台 API 看钱；服务端扣款埋点看不见，绝不混着读。

不求 BI 平台

运营不再手搓拉数：想看什么图，跟 Agent 说一句，当天上线。

选工具的新标准：Agent 能不能完整读到、算得动它的数据 —— 新接一个这样的工具，往往比让 Agent 迁就老工具省时省力得多。PostHog、App Store API 都是这么选的，看板才能「说一句就长出来」。

05老实说

对标 frontier，我还没做好的三件事

Anthropic AI-native SDLC playbook（2026-08）里有、我这套还没有的
GAP 1
Agent 行为的 Eval 回归

改了 CLAUDE.md / skills / hooks，该跑一组真实任务回归 —— 产品效果我有评测集，Agent 行为的改动我还是靠体感。

GAP 2
动作级日志 + 决策抽样

Anthropic 的做法：Agent 每个动作进安全日志、当内部员工一样审计，自动批准的决定定期抽查。我有状态和用量（跑着 / 卡住 / 花了多少），没有动作级日志，也没抽查过它自己拍板的决定。

「接受」没有留痕

制品都有，但计划 / Spec「被接受」只是聊天里一句「可以」，没变成状态或门禁 —— 唯一的硬闸在 commit 门口，前面几道全靠自觉。

05一个动作

每人带走一个动作

把你手上一件重复的事，写成一条 Agent 可执行的验收标准
1
选一件事

每周重复 ≥ 1 次、流程基本固定的 —— 周报拉数、回归检查、素材整理。

2
写清验收

输入是什么 · 步骤有哪些 · 怎样算做对了 —— 写到不用你在场也能判断。

3
跑一遍

交给 Agent 执行，对着验收标准挑错，把错处写回去。

4
固化

能稳定过验收了，就固化成 skill / 定时任务 —— 这件事从此不占你的脑子。

产品回去先做的三件事

灵感一个 issue 一条、不筛选先落库 · issue 三轴标签（环节 × 状态 × 排期）· 方案页 + 图钉批注代替文字评审

研发回去先做的三件事

一分支 = 一目录 = 一会话 · 把「不许 commit」写成 hook 而不是写进 prompt · 写代码的不当 reviewer，换一家模型审

运营回去先做的三件事

先画用户旅程图再定埋点 · 行为口径和钱的口径分开挂牌 · 看板让 Agent 写，想看什么说一句

先做哪个？Anthropic 的落地顺序：先 CLAUDE.md + 一个能跑的验证环，再 plan mode，再并行会话，最后才无人值守 —— 落地顺序 ≠ 生命周期顺序。
